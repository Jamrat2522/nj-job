## C. R1–R8 — งานที่ต้องทำให้ครบก่อนใช้ชื่อ v2-full-*
**สถานะ: ยังไม่เริ่ม — ติดข้อมูล/ไฟล์ต้นฉบับที่ผมยังไม่มี** (ตามวินัย "ห้ามเดา ห้ามมั่ว" ผมจะไม่เขียนโค้ดเดาโครงไฟล์เทมเพลตหรือฟอร์มราชการ)
ตารางนี้ระบุ **สิ่งที่ต้องส่งให้ผมต่อ 1 รายการ** เพื่อเริ่มงานได้ทันทีโดยไม่ต้องเดา:

| รหัส | Module | ต้องการจากคุณ (ครบแล้วเริ่มได้ทันที) | ทำอะไรได้เองก่อน |
|---|---|---|---|
| R1 | REPORT ALL เทมเพลต Excel | ไฟล์ `.xlsx` เทมเพลตจริง 1 ชุด + ไฟล์ผลลัพธ์ที่ V1 export ออกมา 1 ไฟล์ (ไว้เทียบ cell-by-cell) | โครง XML surgery + ตัวเทียบผลอัตโนมัติ |
| R2 | Salary Merge | ไฟล์เงินเดือนจริง 4 ชีตของงวดจริง 1 งวด (ปกปิดเลขบัญชีได้) + ผลลัพธ์ที่ V1 รวมได้ | pipeline ตรวจสอบด้วย openpyxl ก่อนพอร์ตขึ้นเบราว์เซอร์ |
| R3 | WHT50 + SSO | แบบฟอร์ม ภ.ง.ด.1ก/50 ทวิ และ สปส. ที่บริษัทใช้จริง (PDF/Excel) + ตัวอย่างที่กรอกแล้ว 1 ใบ | ต่อ RPC `njhr_wht50_*` (SQL 87 มีครบแล้ว) เป็นหน้าจอ list/draft/confirm ได้เลย |
| R4 | Face Scan | ยืนยันว่าใช้ไลบรารี/โมเดลตัวไหนใน V1 (`face.js`) + นโยบายเก็บ template ใบหน้า + อุปกรณ์ทดสอบ | อ่าน `face.js` ของ V1 แล้วสรุปสถาปัตยกรรมให้ตรวจก่อนพอร์ต |
| R5 | Storage Upload | ชื่อ bucket จริง + นโยบาย/สิทธิ์ที่ตั้งไว้ (ใบรับรองแพทย์ / OT attach / แฟ้มพนักงาน) | repo layer เตรียม `attachAdd/fileSave` ไว้แล้ว รอเสียบ |
| R6 | สลิปเทมเพลตพิมพ์ | สลิปจริงที่พิมพ์จาก V1 1 ใบ (PDF/ภาพ) + โลโก้ความละเอียดสูง | ทำหน้าพรีวิว + CSS `@media print` ให้ตรวจรูปแบบก่อน |
| R7 | Import / Migrate | ไฟล์ Excel นำเข้าพนักงานตัวจริง 1 ไฟล์ + กติกาการจับคู่ซ้ำที่ใช้อยู่ | ต่อ `njhr_emp_import`/`att_migrate` แบบ dry-run ได้ก่อน |
| R8 | Workflow ระบุบุคคล | ตัวอย่างสายอนุมัติจริง 2–3 สาย (แผนก → ใครอนุมัติลำดับใด) | ต่อ `wf_save`/`wf_emp_pool`/`wf_dept_pool` เป็น UI เลือกรายชื่อได้ |

**ข้อเสนอลำดับทำงาน** (ทำทีละกลุ่ม ส่งมอบ + ให้คุณตรวจก่อนไปต่อ):
1. รอบ A — R8 + R3 (ใช้ RPC ที่มีอยู่แล้วบนเซิร์ฟเวอร์ ไม่ต้องรอไฟล์ ยกเว้นแบบฟอร์มพิมพ์ของ R3)
2. รอบ B — R5 + R7 (ต้องการชื่อ bucket + ไฟล์นำเข้าจริง)
3. รอบ C — R1 + R2 + R6 (ต้องการไฟล์เทมเพลต/สลิปจริง — งานเทียบ cell-by-cell)
4. รอบ D — R4 (ต้องมีอุปกรณ์ทดสอบจริง)

## E. ข้อจำกัดที่ต้องรู้ (แจ้งตรง — ไม่ใช่ข้อบกพร่องซ่อน)
1. Maintenance บังคับได้เฉพาะฝั่ง V2: RPC ธุรกิจเดิม (njhr_*) ไม่ถูกบล็อกที่เซิร์ฟเวอร์ระหว่าง Maintenance เพราะห้ามแก้ `njhr_ctx` ที่ V1 ใช้ร่วม (กฎห้ามแตะ V1) — จะปิดช่องนี้ได้เมื่อปลด V1 แล้วเท่านั้น
2. ช่องโหว่ RLS `nj_v6_anon_all` เดิม ยังอยู่ (บันทึกไว้ตั้งแต่ Audit) — แก้ไม่ได้จนกว่าจะย้ายทั้ง 7 แอปออกจาก pattern เดิม
3. โครงคอลัมน์ผลลัพธ์ RPC บางตัว (ชื่อ field ที่ตอบกลับ) อ่านจากการใช้งานใน V1 — โมดูล V2 เขียนแบบยืดหยุ่น (fallback หลายชื่อ field) แต่ต้องยืนยันกับข้อมูลจริงตอนทดสอบ Production
