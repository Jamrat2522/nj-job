# ต้นตอที่แท้จริง: ชั้นระบุตัวตนยังไม่ถูกเชื่อมเลย

## หลักฐานจากระบบจริง

```sql
current_employee_id() → select employee_id from app_users where auth_id = auth.uid()
current_role_name()   → select role        from app_users where auth_id = auth.uid()
```

| ตัวชี้วัด | ค่าจริง | ผลที่ตามมา |
|---|---|---|
| app_users ทั้งหมด | 362 | |
| app_users ที่มี `auth_id` | **2** | `auth.uid()` หาไม่เจอ → ทั้ง 2 ฟังก์ชันคืน NULL กับผู้ใช้ 360 คน |
| app_users ที่มี `employee_id` | **0** | ไม่มีทางรู้ว่า user คนไหน = พนักงานคนไหน |
| leave_requests แถวเดียวที่มี | `employee_id = null` | ข้อมูลลาไม่ผูกกับพนักงาน |

**สรุป**: policy ที่เขียนไว้ดี (`p_emp_select`, `p_leave_all`, `p_att_all`) ใช้งานไม่ได้จริงสักตัว
เพราะเงื่อนไขคืน NULL เสมอ → **นี่คือเหตุผลที่ต้องมี `nj_v6_anon_all` (using=true) ครอบไว้** ไม่งั้นทุกแอปล่ม

⚠️ ดังนั้น **ห้ามลบ `nj_v6_anon_all` ก่อนแก้ชั้นระบุตัวตน** — ลบแล้วแอปทั้ง 7 ตัวหยุดทำงานทันที

## ทางเลือก 3 ทาง (ต้องเลือกก่อนทำอย่างอื่น)

| ทาง | วิธี | ข้อดี | ข้อเสีย / ความเสี่ยง |
|---|---|---|---|
| **A. ย้ายไป Supabase Auth** | สร้าง auth user ให้ครบ 362 คน แล้วเซ็ต `app_users.auth_id` | RLS ทำงานถูกต้องตามที่ออกแบบไว้แล้ว ปลอดภัยสูงสุด | ต้องแก้หน้า login ของ **ทุกแอป** (7 ตัว) · ต้องรีเซ็ต/ย้ายรหัสผ่าน · งานใหญ่ |
| **B. JWT ที่ออกโดย Edge Function** | login ผ่าน Edge Function → ออก JWT ที่มี claim `app_user_id`, `role`, `employee_id` → RLS อ่านจาก `auth.jwt()` | ไม่ต้องย้าย 362 คนไป Auth · แก้เฉพาะจุด login | ต้องเขียน Edge Function + แก้ client ทุกแอปให้ส่ง token · ต้องดูแล secret เอง |
| **C. ปิดเฉพาะจุดเสี่ยงก่อน (ระยะสั้น)** | คงสิทธิ์ anon ไว้ แต่ **เพิกถอนสิทธิ์คอลัมน์อ่อนไหว** (`base_salary`, `national_id`, `password`, `password_hash`, `bank_account`) และให้แอปอ่านผ่าน View ที่ไม่มีคอลัมน์เหล่านี้ | ทำได้ทันที ความเสี่ยงต่อแอปเดิมต่ำ | **ไม่ได้แก้ต้นเหตุ** — ข้อมูลอื่นยังเปิดอยู่ · เป็นแค่การลดความเสียหาย |

**ข้อเท็จจริงที่ต้องยอมรับ**: ตราบใดที่แอปเรียกตารางตรงด้วย anon key ที่ฝังในหน้าเว็บ ความปลอดภัยจริงจะไม่เกิด ไม่ว่าจะเขียน policy ดีแค่ไหน

## ลำดับที่ผมแนะนำ (ถ้าจะให้ปลอดภัยและไม่ล่ม)

1. **เชื่อม `app_users.employee_id` ให้ครบก่อน** — จำเป็นทุกทางเลือก และไม่กระทบแอปเดิมเลย (ดู `12_link_preview.sql` = อ่านอย่างเดียว ดูอัตราจับคู่ก่อน)
2. เลือกทาง A หรือ B (C ใช้ระหว่างรอได้)
3. ค่อยเชื่อมระบบลาของ prototype เข้ากับ `leave_requests` ของจริง

## ข้อมูลเพิ่มที่พบ (มีผลต่อการออกแบบ)

- **กะทำงานจริง 3 กะ**: `OFFICE 08:30–17:30` · `เช้า 08:30–20:00` · `ดึก 20:00–05:00` (ข้ามวัน)
  ทุกกะตั้ง `late_allow_minutes = 0` (prototype ใช้ 15) และมี `ot_start_after` แยกต่างหาก
- **ผู้อนุมัติ**: `leave_approvers` เก็บ config รายแผนก (MANAGER/SUPERVISOR/EXECUTIVE + typeMatrix รายประเภท + `approval_mode: "ALL"` = ต้องอนุมัติครบทุกชั้น)

- ⚠️ `leave_approvers.config` อ้างพนักงานด้วยรหัส 4 หลัก (`"0002"`, `"0155"`) แต่ `employees.emp_code` เป็น `EMP0001`
  → **รหัสคนละระบบ** ต้องยืนยันว่าอ้างถึงตารางไหน (employee_master? ระบบสแกนนิ้ว?) ก่อนใช้งาน
